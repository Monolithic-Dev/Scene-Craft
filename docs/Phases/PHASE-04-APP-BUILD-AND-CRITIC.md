# SceneCraft — Phase 4 Build Spec: App-Build & Critic Agents

> Read `PHASE-03-FRAME-GENERATION.md` (must be complete and passing first), `04-AGENT-ARCHITECTURE.md` §4–5, `10-DIAGRAMS.md` §1–3, and `09-CODING-STANDARDS.md` before starting.

## 0. Premise Correction — Read This First

The original version of this doc assumed a callable "Replit Agent API" (`generate(spec) -> GenerationHandle`, `deploy(handle) -> DeployedApp`) that SceneCraft would invoke per user project to dynamically build and deploy a bespoke previs app. **That API does not exist for a normal Replit account** — confirmed by direct research against docs.replit.com: Replit's Agent is an interactive, browser-based product with no public REST/GraphQL surface for third parties (GraphQL is undocumented/unsupported; an Admin API exists but is Enterprise-only).

More importantly, the hackathon's actual Replit requirement (agentic-cinema.devpost.com/rules, quoted verbatim) is not even asking for that pattern:

> "Replit: your project must be built using Replit Agent as part of the development process, and the finished project must be hosted and deployed directly on Replit (a project URL on a replit.app or replit.dev domain)." / "Projects not deployed on Replit's platform will not meet this requirement, regardless of how the code was written."

"Your project" is **SceneCraft itself** — this is a one-time build-process + hosting-target requirement about the hackathon submission, structurally different from Grafana/Parallel/ClickHouse's genuine runtime API integrations. There's no partner API to wrap.

**This does not mean scaling the phase down.** The previs-app-generation idea is still worth building — it's just SceneCraft's *own* capability now, not a thin wrapper: an agent that turns a film breakdown into real, working frontend code via Gemini is a stronger, more defensible differentiator for "Quality of the Idea" than a wrapper around a third-party black box would have been. Replit's requirement is satisfied separately, honestly, and for real — see §5.

## Objective

Take a project's complete breakdown + frames and turn them into a real, live, navigable previs web app — generated by SceneCraft's own App-Build Agent — then verify, automatically, that the generated app actually reflects what was intended before telling the user it's done.

## Scope

**In scope:** the App-Build Agent (Gemini-driven code generation against a fixed, validated template — not a wrapper around a third-party build API), the Critic/Evaluator Agent (reviews generated output against the source `ProjectState`), the spec-translation layer, the verification/retry loop, the Replit hosting + dev-process track (§5).
**Out of scope:** natural-language iteration (Phase 5 — this phase only handles the *initial* build), the live UI trace panel (still polling-based until Phase 5).

## 1. Design Principle: Constrained Codegen, Not Freeform Eval

Unconstrained LLM-generated code run live in a demo is a reliability risk (the exact failure mode this doc originally tried to avoid by delegating to Replit). The industry-standard pattern for AI app builders (v0, bolt.new, Replit's own Agent) is **constrained scaffolding**: a fixed, pre-tested app shell plus a bounded, validated content/data layer that the LLM fills in — not arbitrary code execution.

SceneCraft's App-Build Agent follows the same pattern:
- The **app shell** (page structure, components, styling, the CSV export button, the scene-navigator/shot-list layout) is a real, version-controlled Next.js template checked into this repo — built once, tested like any other code, never regenerated per project.
- The **data** (scenes, shots, frame URLs, alt-text) is deterministic, directly serialized from the database — never LLM-authored.
- The **only LLM-authored surface** is a bounded per-project customization layer: a short, schema-validated JSON of styling/copy choices (e.g. a title, a tone-appropriate accent color, section ordering) that the shell renders — not raw source code. This keeps generation fast, safe to run live, and trivially reviewable by the Critic Agent, while still being genuinely generative per project rather than a static template with data poured in.

This is a deliberate, stronger reliability posture than the original "send a build instruction to an opaque third-party agent and hope it followed the data-file constraint" design — and it's fully within SceneCraft's own test suite, unlike a third-party black box would have been.

`GenerationJob` gains `deployed_app_url` (already in the Phase 1 schema — now actually populated, pointing at SceneCraft's own generated previs page, e.g. `/projects/{id}/previs`) and `error_detail`. No new tables needed this phase.

## 3. The App-Build Agent (`agents/app_build_agent/`)

**Structure:**
```
agents/app_build_agent/
├── agent.py            # entrypoint: run(project_id) -> BuildResult
├── spec_builder.py       # ProjectState -> deterministic data file (scenes/shots/frames)
├── customization.py       # bounded LLM call -> validated per-project styling/copy JSON
└── prompts.py              # the customization prompt (schema-constrained, see below)
```

**`spec_builder.py`** — deterministic translation layer. Input: the full `ProjectState` (scenes, shots, frame URLs, alt-text). Output: a structured JSON data file, directly serializable from the database. No LLM involved here — this must never drift or hallucinate.

**`customization.py` / `prompts.py`** — the bounded generative layer. Given the project's title, style reference, and genre/tone cues from the breakdown, produce a small JSON object validated against a strict schema (e.g. `{title: str, accent_color: str (hex), tone_note: str (<=140 chars)}`) — reject and retry once on schema-validation failure, then fall back to sensible defaults (never block the job on a styling call). This is the one place an LLM touches the previs app, and it can never affect app *structure*, only presentation values the shell already knows how to render.

**Rendering:** the previs app is `apps/web`'s own `/projects/{id}/previs` route, reading the data file + customization JSON server-side — not a separately generated/deployed artifact. This means "generating the app" is really "generating this project's content for an already-built, already-tested page," which is what makes the Critic Agent's job tractable and the whole thing safe to run live.

## 4. The Critic / Evaluator Agent (`agents/critic_agent/`)

**Structure:**
```
agents/critic_agent/
├── agent.py           # entrypoint: run(project_id) -> Verdict
└── comparator.py         # structural comparison: rendered data vs. expected ProjectState
```

**`agent.py` flow:**
1. Load the data file `spec_builder.py` produced and the customization JSON.
2. Compare shot/scene coverage against the expected `ProjectState` (`comparator.py`) — every non-`needs_review` shot must have a frame and be present in the data file; every scene must be represented.
3. Validate the customization JSON against its schema (catches a case where the bounded LLM call silently produced something malformed that slipped past retry).
4. Return a `Verdict`: `{passed: bool, missing_shots: list[str], schema_errors: list[str], notes: str}`.

**On failure:** hand the verdict back to the App-Build Agent as corrective context and trigger exactly one retry (re-run `spec_builder.py`/`customization.py`). If the retry also fails, the Coordinator marks the job `FAILED_NEEDS_REVIEW` with the Critic's notes attached — **never silently mark a broken previs page as complete.** This is the single most important behavior in this phase, carried over unchanged from the original design: shipping broken output is worse than an honest failure state.

## 5. Satisfying the Real Replit Requirement

Two separate, genuine deliverables — tracked here but not gated on the App-Build/Critic agents above, since they're a one-time submission-level concern, not a per-project runtime one:

**5a. Hosting.** Deploy SceneCraft's own web app on Replit's platform to get a real `replit.app`/`replit.dev` URL: import this GitHub repo via Replit's Guided Import (`replit.com/import`), configure a Reserved VM deployment (needed for a persistent process, not just a static build — `apps/web` talks to `apps/api`). Keep it in sync with ongoing GitHub-based development using the open-source [`repl.deploy`](https://github.com/khrj/repl.deploy) GitHub Action — a daemon running inside the Reserved VM Repl that polls this repo and restarts on push. There is no first-party programmatic deploy-trigger for a normal account (confirmed against docs.replit.com); this is the legitimate, available substitute rather than a manual re-click per change.

**5b. Development process.** Replit's Agent itself has no programmatic or browser-automation access path we've found (and driving a vendor's production AI chat product via unauthorized automation isn't something to pursue even if it were technically possible). This part is inherently a human-driven session in Replit's real UI. Concretely: use Replit's Agent to build a genuine, bounded piece of this project — a good fit is the app-shell template from §1 (the Next.js previs page structure/styling) — then merge the resulting code back into this repo through the normal branch/PR workflow, same as any other change. This is tracked as its own task, not blocked on or blocking the agent work above.

## 8. Required Tests

**Spec translation (pure unit tests):**
- `test_spec_builder_produces_valid_json_data_file` — given a known `ProjectState`, assert the output JSON matches the schema the previs page expects
- `test_spec_builder_includes_flagged_shots_with_marker` — shots flagged `needs_review` from Phase 2/3 are included with a visible "under review" marker, not silently dropped

**Customization layer (mocked Gemini):**
- `test_customization_validates_against_schema` — a well-formed model response passes validation
- `test_customization_retries_once_then_falls_back_to_defaults` — malformed JSON on first call, still malformed on retry → sensible defaults used, job does not fail

**App-Build Agent:**
- `test_app_build_produces_data_file_and_customization` — end-to-end (mocked Gemini) produces both artifacts for a known project

**Critic Agent:**
- `test_critic_passes_on_matching_content` — data file matches expected `ProjectState` exactly → `passed: True`
- `test_critic_detects_missing_shot` — data file missing one shot → `passed: False`, `missing_shots` populated correctly
- `test_critic_detects_schema_violation` — malformed customization JSON that slipped past retry → `passed: False`, `schema_errors` populated
- `test_critic_triggers_exactly_one_retry_on_failure` — integration test confirming the retry-then-escalate behavior, not infinite retries
- `test_critic_failure_after_retry_marks_needs_review` — job ends in `FAILED_NEEDS_REVIEW`, not silently `COMPLETE`

**End-to-end (mocked LLM/Imagen):**
- `test_full_initial_generation_produces_deployed_url` — script upload through to a `deployed_app_url` on the project, exercising the full `[breakdown, frames, app_build, critic]` chain from `10-DIAGRAMS.md` §3
- `test_previs_route_renders_generated_project` — a real (test-client) GET of `/projects/{id}/previs` renders the expected scenes/shots/frames

## Definition of Done

- [ ] All Phase 1–3 checks still pass
- [ ] All tests above pass
- [ ] A real project produces a genuinely working, navigable previs page at `/projects/{id}/previs` matching the layout in the original §3 build instruction (scene navigator, per-shot frame/action/camera/characters, CSV export)
- [ ] Deliberately breaking one shot's data (manual test) causes the Critic Agent to catch it and trigger the retry path — observe this happen, don't just trust the test suite
- [ ] A job that can't be fixed after retry ends in `FAILED_NEEDS_REVIEW` with a genuinely useful `error_detail`, not a generic "something went wrong"
- [ ] §5a: SceneCraft is actually reachable at a `replit.app`/`replit.dev` URL
- [ ] §5b: at least one real, merged PR whose code was authored via a genuine Replit Agent session

## Common Pitfalls

1. **Letting the customization layer grow beyond bounded styling values into structural/code changes** — the moment the LLM output can change *what* renders rather than just *how* it looks, the Critic Agent's job stops being tractable and reliability risk creeps back in. Keep the schema tight.
2. **Marking a job complete as soon as the data file is written** — a file existing is not the same as the app being correct. The Critic Agent's pass is what should gate `COMPLETE`.
3. **Unbounded retries between Critic and App-Build** — without an explicit retry counter, a systematically broken project can loop forever. One bounded retry, then escalate — no exceptions.
4. **Treating §5 as a checkbox** — "used Replit Agent once for a trivial change" technically satisfies the letter of the rule but not its spirit, and judges are explicitly told to scrutinize partner depth. Give Replit Agent something genuinely worth building (the app shell itself is a good match: real, load-bearing, and visibly Replit's contribution).
